# 平衡树任务的输出修正流程修复

2026-10-11。

教师的平衡树备课任务 `f4243780-40b9-491c-a340-6fd953173f34` 曾在第二轮修正失败：已有 106 页草稿，完成 19/22 批、累计 34 次调用；“修正预期输出”返回输出页补丁，被误判为缺少 `code.source`。

原因有两处：代码要求只检查本次返回的页面，忽略同一程序已经存在且保留的源码；自动扩展代码组修改范围时，又把未出错的源码页都当成必须修改的目标。正确的输出补丁因此被反复拒绝，错误反馈反过来要求模型重复提供源码。

修复后，代码要求检查补丁应用后的实际目标内容：同一程序的源码可以保留，输出文本不能冒充源码，也不能借用无关程序满足代码要求。修正步骤分别保存必须修正的页面和可修改的完整代码组范围；正确的关联页面可以不改。同一程序的修正批次即使从输出页开始，也能合并处理；只修改输出时提供完整程序作为只读上下文。

旧检查点中的输出修正目标和相应错误反馈在恢复时兼容处理，无需重建整份课件。仍要求真正出错的目标被修改，并继续检查范围、页面存在性、数据格式及版本冲突。代码讲解主页与其自动生成的代码续页也作为同一份内容判断，修改讲解或输出说明时无需重复返回程序。

恢复真实任务后还暴露了动态拆批的范围错误：格式异常使两页修正拆成两个单页批次，但必须修正的目标列表仍包含两页，导致“必须改两页”与“一批最多一页”相互冲突。现在拆批同时分配必须修正的目标，旧检查点恢复时也将目标限定到当前批次。

验证：195/195 项单元与接口测试、37/37 条 Chrome 流程通过。新增测试覆盖输出修正保留源码、扩展范围不用全部改写、输出优先的小批次、输出不能冒充程序、无关程序不能满足要求、动态拆批范围、修改讲解主页保留其程序，以及旧任务恢复。浏览器使用明确的模型夹具走通生成 → 发现输出问题 → 只改输出 → 检查 → 原子提交 → 刷新。

另使用本次真实失败任务的副本复现卡点，单个输出补丁被接受，原 106 页和所有非输出页逐字保留，未写入真实任务。证据为 `artifacts/balanced-tree/output-repair-functional.json`。第二次使用拆批失败后的副本验证单页补丁、当前批次目标与源码保留，证据为 `split-repair-functional.json`。这两项验证只证明应用功能，不核验课程算法或输出的教学正确性。

真实任务恢复前，工作空间与任务文件已完整备份至 `data/backups/*-before-output-repair-1791711759152.json`，修复拆批后再次恢复前也备份至 `*-before-split-repair-1791712028300.json`。

真实恢复结果：两个功能卡点均通过，全部 26/26 批完成，草稿 119 页，累计 53 次调用。最终模型检查仍报告 4 项内容问题，已达到配置的 3 轮修正额度，任务仍为失败，课件未提交。检查中曾将同页包含多个完整函数当作缺陷，已补充检查提示词：允许一页或一个代码块包含多个完整函数，按整个 blockId 的程序检查，不要求每个展示分段独立编译，不因正常函数分页反复改写。

按教师要求，本轮没有进一步开展算法或输出正确性研究，也没有提高修正额度或强行将草稿提交为通过。最新状态与真实页面验证记录在 `artifacts/balanced-tree/task-result.json`、`live-functional-result.json`。
